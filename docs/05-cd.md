# 05 · CD hacia la VM

Cada `push` a `main` termina desplegado en la VM `MaquinaVirtual-nain` sin intervención manual:

```
push a main ──► build-and-push (ubuntu-latest)          ──► deploy (runner self-hosted en la VM)
                build + tests + imágenes a Docker Hub        git pull → docker compose pull/up → verificación → rollback si falla
                tags: latest y sha-<commit>
```

## Alternativas evaluadas

| Alternativa | Resultado |
|---|---|
| SSH desde el pipeline (`docker compose pull` + `up -d`) | **Descartada.** La VM tiene IP privada (`10.56.31.44`, interfaz `enp1s0`) y sale a internet por NAT (`157.92.6.49`). Los runners de GitHub no pueden entrar: el job falló con `dial tcp ...:22: i/o timeout`. Abrir el 22 a internet no depende del grupo y además agranda la superficie de ataque. |
| Runner self-hosted en la VM | **Elegida.** El runner abre una conexión **saliente** HTTPS hacia GitHub y espera trabajos; no hace falta abrir ningún puerto entrante. |

## Acceso y credenciales

- El runner corre como servicio de systemd con el usuario `Gabo`, que ya puede usar `docker` sin `sudo`.
- Está registrado solo en este repo, con la etiqueta `picopark-vm`. Únicamente el job `deploy` lo usa; el build sigue en `ubuntu-latest`.
- Como el repo es público, el job `deploy` solo corre con `push` a `main` (nunca con un pull request), y en *Settings → Actions → General* está activado pedir aprobación para workflows de forks de colaboradores externos. Así nadie de afuera ejecuta código en la VM.
- Se dio de baja el acceso SSH del pipeline: se borró el secreto de la clave y la línea de `id_ed25519_cd` en `~/.ssh/authorized_keys`.

## Variables y secretos

| Dónde | Qué |
|---|---|
| GitHub → Secrets | `DOCKERHUB_USERNAME`, `DOCKERHUB_TOKEN` (token de acceso de Docker Hub, no la contraseña). Se pasan al paso como variables de entorno y `docker login --password-stdin`, así no aparecen en el comando ni en los logs. |
| VM → `/opt/proyecto/PICO_PARK/.env` | Configuración no secreta (puertos, IP), según `.env.example`. No se versiona. |
| Pipeline → `IMAGE_TAG` | La versión a desplegar (`sha-<commit>`). La lee `docker-compose.yml` con `${IMAGE_TAG:-latest}`. |

## Estrategia de actualización

1. `git pull --ff-only` en la VM para traer el `docker-compose.yml` y el script al día.
2. `scripts/deploy.sh sha-<commit>` hace `docker compose pull` y `up -d` con la imagen **exacta del commit**, no `latest`. Así se sabe siempre qué versión corre, y la que estaba antes sigue disponible.
3. `concurrency: deploy-vm` impide dos deploys en paralelo.
4. Es un reemplazo directo (recreate): hay unos segundos de corte mientras arrancan los contenedores nuevos. Para el alcance del proyecto se considera aceptable.

## Verificación posterior al despliegue

El script espera hasta 60 s a que:
- `docker compose ps` muestre los dos servicios en estado `running`, y
- `http://localhost:4321/` (juego) y `http://localhost:3002/` (servidor) devuelvan una respuesta HTTP.

Cada deploy queda registrado en `.deploy/deploy.log` con fecha, versión nueva, versión anterior y resultado. La versión activa está en `.deploy/current`.

## Recuperación ante una versión fallida

- **Automática:** si la verificación falla, el script imprime los logs de los contenedores, vuelve a levantar la versión anterior (`.deploy/current`) y termina con error, así el pipeline queda en rojo.
- **Manual:** desde la VM se puede volver a cualquier versión publicada:
  ```bash
  cd /opt/proyecto/PICO_PARK
  bash scripts/deploy.sh "sha-$(git rev-parse d562bdf)"
  ```
  Los tags usan el hash completo del commit (`sha-<40 caracteres>`), por eso se obtiene con `git rev-parse`.
  Las imágenes viejas no se borran (`docker image prune` solo elimina las huérfanas), así que el rollback funciona aunque Docker Hub no responda.

## Evidencia

1. Un commit a `main` y la ejecución en *Actions*: `build-and-push` en verde, después `deploy` corriendo en `picopark-vm`.
2. En la VM: `docker compose ps` muestra las imágenes con el tag `sha-<commit>` del push, y `cat .deploy/deploy.log` muestra el registro.
3. Prueba de rollback, simulando que la versión nueva no pasa la verificación:
   ```bash
   SIMULAR_FALLO=1 bash scripts/deploy.sh "sha-$(git rev-parse d562bdf)"
   ```
   El log muestra `FALLÓ la verificación` y después `Rollback OK`, y `docker compose ps` vuelve a mostrar la versión que estaba antes.
